\section{Prototype objective}
The prototype exercises the minimum workflow for coordinating a shared campus ride. A requester needs to find a suitable trip and receive a clear decision. An organiser needs to control which requests are accepted and how many seats remain available.

\section{Workflow and acceptance checks}
\begin{enumerate}
\item Sign in with two test Thapar accounts. Confirm that the authentication flow requires a valid one-time code.
\item As the organiser, publish a ride with a pickup point, destination, departure time and available seats.
\item As the requester, find the ride and submit a seat request. Confirm that its status appears as pending.
\item As the organiser, accept or decline the request. Confirm that the requester can see the decision and that an accepted request consumes an available seat.
\item Repeat with the final seat and a second requester to check capacity. Try deciding a request from an account that does not organise the ride to check authorisation.
\end{enumerate}

\section{Implementation evidence}
The current repository contains the Next.js ride list, ride form and ride detail screens, a FastAPI rides router, SQLAlchemy models, database migrations and backend API tests. These files support the workflow described here. This report documents the core prototype scope through the corresponding screens, API and persistence components.

\section{Verification approach}
The repository includes tests for email eligibility, OTP handling, ride workflows and fare splitting. Acceptance checks cover pending requests, organiser decisions, seat availability and restricted actions. The walkthrough above defines expected behaviour for the prototype and regression checks for later increments.

\section{Improvement plan}
\begin{itemize}
\item Add activity listings and reuse the discover--request--decide workflow without fare tracking.
\item Add notifications and secure chat so confirmed participants can coordinate details.
\item Record actual fare shares after completion and require the organiser to confirm each rider's payment status.
\item Check the complete ride-request workflow after integration and review any stage where participation states become inconsistent.
\end{itemize}
